# Module 05 — Decision memo

**To:** Yasmin Kaya, Operations Lead  
**From:** Adam Salman  
**Subject:** Keep normalized operations, serve the dashboard from a refreshed report table

I recommend keeping `machine`, `job`, `part`, and `job_part` in **3NF** as the transactional source of truth, while using `report_jobpart` as a deliberate, read-only reporting snapshot. In a local benchmark of the 200,000-row setup, the four-table join took **65.2 ms** and the reporting table took **57.6 ms** (warm-cache medians of five runs), so the read improvement was modest, **about 1.13×**, not a guaranteed dramatic speedup. The key cost is consistency: moving one machine's site updates **one normalized row** but **4,000 reporting rows**; the measured base-table storage was **3,976 KiB** for the four 3NF tables versus **10,832 KiB** for the denormalized table (indexes excluded). Dropping the reporting machine index improved the report scan to approximately **42.8 ms** on the test host, showing that an index can hurt an aggregate that touches most rows. I would rebuild the reporting table in a transaction on a schedule after the shift and atomically swap the new snapshot into use, keeping the operational workload on the normalized tables. The refresh job should log a timestamp, source row count, destination row count and aggregate sum, then alert if a check fails. If that refresh becomes stale, the dashboard can show yesterday's machine site or pricing, so it needs a clearly displayed **last refreshed** timestamp and an agreed maximum age. These results were collected locally in an automated run, not in the classroom; the team should rerun the benchmark on the target laptop or production-like hardware before committing to the architecture.
